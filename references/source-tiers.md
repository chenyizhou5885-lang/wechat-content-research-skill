# 检索能力档位与材料说明

## 为什么要分档

同一份报告，可能是接了正规数据服务跑出来的，也可能是搜狗只捞到三篇凑出来的。两者长得一样才是最危险的事。所以每轮开始先确认这次能用什么，结束时如实写清楚。

## 开工先探测，不要开场盘问

```bash
python3 scripts/detect_capability.py --task-dir .
```

脚本只判断能力在不在，不读取、不打印、不落盘任何凭证值。返回三档：

| 档位 | 含义 | 能不能按账号查文章 |
| --- | --- | --- |
| `mp_data_source` | 已配置公众号数据服务 | 可以 |
| `user_supplied` | 用户提供了校准样本或导入文章 | 只能查用户给的范围 |
| `search_only` | 只有宿主检索加内置搜狗召回 | **不能** |

把结果写进 `raw_sources.json` 的 `capability` 段。

**不要在会话开头问用户有没有 API。** 探测不到就静默按 `search_only` 开工。只有当本轮结果确实不够用时，才顺势提一句：

> 公众号这块只找到 2 篇。如果你们有新榜这类数据服务，接上能覆盖得更全，要配吗？

用户配置过一次就记住，不要每轮重复问。

## 密钥不经手

凭证只从环境变量读取，skill 不写入任何文件、不回显值。需要接入公众号数据服务时，按 WorkBuddy Connector 规范单独接入并由用户完成授权；本 skill 只负责探测「有没有」，不负责保管。

## 能力边界要说在前面

微信官方没有开放读取他人公众号历史文章的途径，这是它刻意不开放，不是脚本能绕过的技术问题。

所以「看某个指定公众号最近讲这个话题的文章」这件事：

- `mp_data_source` 档可以做到
- `user_supplied` 档只能在用户给的范围内做到
- `search_only` 档做不到，只能靠多组关键词提高命中概率

搜不到不等于对方没写过。报告里必须这么写，不能让用户误以为「没搜到」就是「不存在」。

## 材料说明写什么

每份调研报告开头第一节固定叫「材料说明」，放在最显眼处，不要放脚注。用人话写四件事：

1. 这轮实际用了哪些渠道。
2. 名单里哪些账号没搜到，并说明搜不到不等于没写过。
3. 哪些结论可以直接引用。
4. 哪些只能当线索，还需要补什么。

示例：

> 这次公众号部分只用了搜狗搜索，找到 3 篇。名单里有两个号没搜到相关文章，但这不代表它们没写过，可能是搜不出来。
>
> 所以：报告里「同行都怎么讲这个话题」这部分只基于 3 篇，参考价值有限。市场规模那个数字来自机构官方原文，可以直接引用。

`validate_research.py` 会检查这一节存在，缺了直接拦住。
